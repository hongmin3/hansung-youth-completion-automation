이 문서는 dimode-completion-input가 어떻게 동작해야 하는가를 정의하는 기준이다. 코드가 현재 그렇게 동작한다는 사실은 사양이 아니다. 사양과 구현이 다르면 코드에 맞춰 이 문서를 고치지 말고 SPEC / CODE MISMATCH로 식별한다 — 절차는 AGENTS.md에 있다.

프로젝트 규모에 따라 아래 Section은 줄일 수 있다. 다만 1 목적 · 2 범위 · 5 기능 요구사항 · 9 오류 처리 · 11 테스트 사양 · 12 추적성은 유지보수형 자동화라면 반드시 채운다.

1. 목적

청년부 교육 담당자가 Google Sheet에 모아 둔 양육 수료자 명단을, 사람이 디모데 웹 화면에서 한 명씩 검색·입력하는 대신 자동으로 등록한다. 수백 행 규모의 반복 입력에서 사람이 저지르는 동명이인 오입력과 중복 입력을 없애는 것이 목적이다.

성공 조건: 명단의 각 행이 확정된 동일인에게만 수료내역으로 등록되고, 등록에 성공했거나 이미 같은 과정이 등록되어 있던 행만 Sheet의 입력여부가 체크된다. 확정하지 못한 행은 입력하지도 체크하지도 않고 사유가 남는다.

2. 프로젝트 범위

포함

  • Google Sheet(또는 동일한 열 구조의 CSV)에서 수료자 명단을 읽는 것.
  • 디모데 청년관리 > 교인검색(청년) 화면에서 명단의 사람을 찾아 동일인으로 확정하는 것.
  • 허용된 청년- 교육과정에 한해 수료내역을 등록하는 것.
  • 같은 과정이 이미 등록되어 있는지 확인해 중복 등록을 막는 것.
  • 성공한 행에 한해 Sheet의 입력여부 체크박스와 보완된 전화번호를 갱신하는 것.
  • 행 단위 처리 결과를 CSV와 로그로 남기는 것.
  • 실제 입력 없이 대상과 판정 결과만 확인하는 드라이런.

제외

  • 명단 자체의 수집·정제. 시트 내용의 오탈자 교정은 사람이 한다.
  • 디모데에 존재하지 않는 교인의 신규 등록. 교인 생성은 하지 않는다.
  • 기초반, 예배학교, 결혼예비학교의 입력. 현재 명시적 제외 대상이다.
  • 수료 외 상태(미수료, 수강중 등)의 등록.
  • 교육과정 삭제·수정. 이 자동화는 신규 등록만 한다.
  • 스케줄 실행·무인 실행. 사람이 지켜보는 상태에서 수동 실행한다.
  • Apps Script 영역. 그 기준은 ../newacts-newcomer-automation/에 있다.

외부 시스템 경계는 셋이다.

  1. Google Sheets — 명단의 원본이자 입력여부의 기록처. Sheets API(OAuth) 또는 CSV export로 읽고, 쓰기는 Sheets API로만 한다.
  2. 디모데 웹(청년 관리) — Playwright Chromium으로 조작하는 ASP.NET 프레임 기반 화면. 공개 API가 없으므로 DOM selector에 의존한다.
  3. 로컬 파일 시스템 — 설정, OAuth 자격 증명, 결과 CSV, 실행 로그.

4. 전체 동작 흐름

  1. CLI 옵션을 해석해 실행 모드(드라이런/실제 입력)와 대상 범위를 정한다.
  2. Google Sheets 자격 증명을 준비한다. 실제 입력 모드에서는 필수다(단, 체크 보류 옵션 제외).
  3. 명단을 읽는다. 각 행에 원본 시트의 행 번호를 붙인다.
  4. Playwright로 Chromium을 띄우고 디모데에 로그인해 교인검색(청년) 목록으로 이동한다.
  5. 행마다:
    1. 입력여부가 이미 체크되어 있으면 건너뛴다.
    2. 구분을 허용 교육과정으로 매핑한다. 매핑이 없거나 제외 대상이면 교육과정매핑없음.
    3. 전화번호가 비어 있고 보완 조회가 켜져 있으면 이름·군·A/B로 전화번호를 보완한다.
    4. 전화번호가 있으면 전화번호로 검색해 이름+전화번호가 유일하게 맞는 사람을 찾는다.
    5. 찾지 못했으면 이름으로 검색해 이름+군이 같고 교인 구분이 청년 A/B인 사람이 정확히 한 명일 때만 확정한다.
    6. 확정하지 못했거나 복수면 입력하지 않고 사유 상태를 남긴다.
    7. 드라이런이면 드라이런확인으로 끝낸다.
    8. 실제 입력이면 교인 상세 창을 열어 같은 과정이 있는지 보고, 없을 때만 저장한다.
    9. 저장 성공 또는 기존 등록 확인 뒤에만 Sheet의 입력여부를 체크한다.
  6. 브라우저를 닫고 행 단위 결과를 output/ 아래 CSV로 저장한다.

5. 기능 요구사항

ID 규칙: REQ-<CATEGORY>-NNN. CATEGORY는 대문자·숫자, NNN은 세 자리. 한 번 부여한 ID는 재사용하거나 의미를 바꾸지 않는다. 삭제한 ID를 다른 기능에 돌려쓰지 않는다.

REQ-SHEET-001 수료자 명단 읽기

verified구현 completion_automation.py (load_sheet_rows)테스트 TEST-DRYRUN-001 (수동)참조됨 REQ-SHEET-002, TEST-DRYRUN-001변경 이력 CHANGELOG에 이 ID로 기록된 변경 없음

목적

수료자 명단을 고정된 열 구조로 읽고, 각 행을 원본 시트의 행 번호와 묶어 둔다.

동작

  • 입력 원본은 세 가지 중 하나다: (a) Sheets API로 읽은 대상 탭의 A:G 범위, (b) --sheet-csv로 지정한 CSV 파일, (c) OAuth 자격 증명이 없을 때 쿠키로 내려받은 CSV export.
  • 열 순서는 구분 / 군 / 팀 / 이름 / 핸드폰 / 담당자 / 입력여부여야 한다.
  • 첫 행은 header로 보고, 데이터 행에는 시트 기준 행 번호(2부터)를 부여한다. 이 번호가 뒤의 시트 갱신과 결과 CSV의 시트행 값의 기준이다.
  • API 응답에서 뒤쪽 빈 칸이 생략되어 열 수가 모자란 행은 빈 문자열로 채워 header와 길이를 맞춘다.

기대 결과

명단의 모든 데이터 행이, 원본 행 번호를 잃지 않은 채 처리 대상 목록으로 올라온다.

예외 처리

  • SHEET_URL에서 스프레드시트 ID를 뽑을 수 없으면 실행을 중단한다.
  • 쿠키 방식에서 401이 오면 쿠키 만료임을 알리고 OAuth 설정을 안내하며 중단한다.
  • --sheet-csv는 원본 시트의 전체 행 순서를 보존한 CSV에만 쓴다. 필터링된 CSV를 주면 시트행 번호가 어긋나므로 사용자가 보장해야 한다.

관련 구현

completion_automation.py — load_sheet_rows, rows_from_csv, spreadsheet_id_from_url, gid_from_url

목적

기본값을 안전한 쪽(읽기 전용)에 두고, 실제 데이터 변경은 명시적 옵션으로만 일어나게 한다.

동작

  • 옵션 없이 실행하면 드라이런이다. 디모데와 Sheet를 변경하지 않는다.
  • --execute를 줄 때만 디모데 저장과 Sheet 체크를 수행한다.
  • --limit N은 실제로 처리한 행이 N개가 되면 멈춘다. 건너뛴 행(체크 완료 행)은 세지 않는다.
  • --skip-phone-lookup은 전화번호 보완 조회를 생략한다(REQ-PHONE-001).
  • --sheet-csv PATH는 Sheet 대신 CSV를 입력으로 쓴다.
  • --defer-sheet-checks는 Sheets 자격 증명 없이 --execute를 허용하고, 체크 갱신을 외부 작업으로 미룬다. 일반 실행에서는 쓰지 않는다.

기대 결과

실행 시작 시 모드와 대상 행 수가 로그에 남는다. 옵션을 잘못 조합해도 드라이런이 실제 입력으로 바뀌지 않는다.

예외 처리

  • Playwright가 설치되어 있지 않으면 설치 명령을 안내하고 종료한다.
  • --execute이면서 --defer-sheet-checks가 아닌데 OAuth 클라이언트 파일이 없으면 입력을 시작하지 않고 중단한다.

main.py, completion_automation.py — parse_args, Options, main

목적

이미 처리된 행과 입력해서는 안 되는 교육과정을 처리 대상에서 제외한다.

동작

  • 입력여부가 체크로 해석되는 값이면 그 행은 검색조차 하지 않고 건너뛴다. 체크로 보는 값은 TRUE, Y, YES, 완료, 입력완료, 체크 기호이며 대소문자를 구분하지 않는다.

  • 구분 값을 교육과정 매핑으로 변환한다. 기본 허용은 다음 다섯 개다.

    시트 구분디모데 과정
    LTC청년-LTC
    확신반청년-확신반
    성장반청년-성장반
    성경대학청년-성경대학
    교리대학청년-교리대학

  • 설정으로 매핑을 추가할 수 있으나, 제외 목록(기초반, 예배학교, 결혼예비학교)은 설정으로 추가하더라도 코드가 다시 제거한다. 설정으로 제외를 뚫을 수 없어야 한다.

  • 매핑 결과가 없거나 청년-으로 시작하지 않으면 교육과정매핑없음으로 남기고 입력하지 않는다.

기대 결과

9. 오류 처리 정책

  • 재시도하지 않는다. 검색·저장 실패를 자동으로 다시 시도하지 않는다. 재시도는 사람이 원인을 확인한 뒤 프로그램을 다시 실행하는 방식으로만 한다. 중복 방지(REQ-INPUT-001)가 재실행을 안전하게 만든다.
  • 부분 성공을 허용한다. 확정 실패, 복수 일치, 과정 미매핑은 그 행의 상태로 기록하고 다음 행으로 넘어간다. 한 사람 때문에 전체 실행을 멈추지 않는다.
  • 중단 기준. 다음은 행 단위 상태가 아니라 실행 중단 사유다.
    • SHEET_URL에서 스프레드시트 ID를 얻지 못함.
    • 쿠키 만료(401)로 명단을 읽지 못함.
    • --execute인데 필요한 OAuth 클라이언트 파일이 없음.
    • Playwright 미설치.
    • 로그인 실패나 화면 구조 변경으로 검색 화면에 도달하지 못함.
  • 기록 위치. 행 단위 결과는 output/의 CSV와 result_log.txt에 남는다. 로그는 행마다 즉시 append 하므로 중단되어도 진행 지점을 알 수 있다. 단, 결과 CSV는 실행이 끝까지 진행돼야 저장된다.
  • 선택자 실패. 디모데 화면 구조 변경이 의심되면 실제 입력을 멈추고 드라이런부터 다시 확인한다. 증거 없이 선택자를 바꾸지 않는다.

10. 보안 요구사항

  • 인증 수단은 둘이다: 디모데 ID/비밀번호(설정 파일), Google Sheets OAuth 토큰(로컬 JSON). 쿠키 방식은 드라이런의 임시 수단으로만 허용하고 운영에는 쓰지 않는다.
  • 저장소에 들어가면 안 되는 것: config.py, OAuth 클라이언트·토큰 JSON, 쿠키 값, output/, user_data/, result_log.txt, 디버그 HTML·이미지.
  • 접근 범위: Google 쪽은 Sheets scope 하나, 디모데 쪽은 해당 계정이 원래 가진 청년관리 권한을 넘지 않는다. 이 자동화는 권한을 확대하지 않는다.
  • 토큰은 만료 시 refresh token으로 갱신하고, 갱신 결과를 같은 로컬 파일에 다시 쓴다.
  • 에이전트는 설정 파일과 자격 증명 파일의 내용을 열어 응답에 싣지 않는다.

13. 미확정 사항

  • 수료일·수료연도가 코드 상수다. 20260621 / 2026이 고정되어 있어 다음 기수에는 반드시 코드를 고쳐야 한다. 설정 항목이나 CLI 인자로 빼야 하는지, 그렇다면 시트의 열로 받아야 하는지 정해지지 않았다.
  • 제외 교육과정의 최종 처리. 기초반, 예배학교, 결혼예비학교는 "추후 확정 후 사용자 요청 시"로만 적혀 있다. 디모데의 정확한 과정 명칭도, 입력할지 여부도 미확정이다.
  • 호출되지 않는 팀 비교 함수. 확정 경로는 이름 + 군 + 청년 A/B이고 팀은 판정에 쓰지 않는다(2026-09-19 확정, 문서를 코드에 맞춤). identity_matches, normalize_team은 정의만 되어 있고 호출되지 않는다 — 지울지, 시트 소속 확인용으로 쓸지는 정해지지 않았다.
  • --defer-sheet-checks의 후속 절차. 미룬 체크를 누가 어떤 방법으로 맞추는지 정해진 절차가 없다. 또한 이 옵션을 켜도 OAuth 파일이 존재하면 체크가 그대로 수행되는데, 이것이 의도인지(자격 증명이 있으면 체크한다) 아니면 항상 보류해야 하는지 확정되지 않았다.
  • 자동 테스트 도입 범위. 현재 테스트가 없다. 순수 함수(format_phone, normalize_group, is_checked, course_map)만 단위 테스트로 덮을지, Playwright 경로도 대상으로 할지 결정되지 않았다.
  • 결과 CSV와 실행 로그의 보존 기간. 개인정보를 담는데 정리 주기나 삭제 기준이 없다.
  • Owner. 저장소에 운영 책임자가 명시되어 있지 않다.
